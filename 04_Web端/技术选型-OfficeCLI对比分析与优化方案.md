# 技术选型：OfficeCLI 对比分析与我们的优化方案

> 项目：广东石油化工学院 校素拓质检部 周工作平台（`04_Web端/`）
> 分析对象：[iOfficeAI/OfficeCLI](https://github.com/iOfficeAI/OfficeCLI)
> 实测环境：Windows / OfficeCLI `v1.0.152` / Python 3.13 + openpyxl
> 撰写日期：2026-09-29

---

## 一、结论先行

| 结论 | 说明 |
| --- | --- |
| **OfficeCLI 值得借鉴，但不适合替代我们现有的写入链路** | 它强在「读 / 渲染 / 校验 / 原子操作」，弱在「按我们固定模板批量写列」 |
| **最终定位** | OfficeCLI 只承担两件事：**高保真渲染**（网页内预览）和 **OpenXML 结构校验**（下载前体检）；写入仍由 openpyxl 负责 |
| **借鉴它的 4 个设计思想** | ① 稳定 ID 寻址（不依赖行号）② 原子写入 + 自动备份 ③ 内置渲染引擎 ④ 结构校验门禁 |
| **已落地** | P0 可靠件改造 + P1 网页内预览 / 体检，均已实测通过 |

一句话：**照搬它的"思想"，不照搬它的"实现"。**

## 二、OfficeCLI 是什么

| 项目 | 事实（实测 / GitHub API） |
| --- | --- |
| 仓库 | `iOfficeAI/OfficeCLI` |
| 语言 / 许可 | C# / **Apache-2.0**（可商用、可分发） |
| 星标 | **31,427** |
| 形态 | **单文件二进制**（实测 `officecli.exe` 33.4 MB），**不需要装 Office** |
| 覆盖格式 | `.docx` / `.xlsx` / `.pptx` |
| 官方定位 | "the first and best Office suite purpose-built for **AI agents**" —— 面向 AI/Agent 的 Office 套件 |

它不是给人点的软件，而是给**程序/Agent**用的 Office 操作层，这点与我们的自动化诉求天然契合。

---

## 三、功能盘点（能力地图）

按官方 `--help` 实测整理，共 20+ 个动词：

| 类别 | 命令 | 作用 |
| --- | --- | --- |
| **查** | `get` / `query` / `view` / `raw` | 按路径取节点、CSS 式选择器查询、多模式查看、看原始 XML |
| **改** | `set` / `add` / `remove` / `move` / `swap` | 改属性、加元素、删元素、移动、交换位置 |
| **批量** | `batch` | 一个 JSON 数组跑多条命令，**全成功或整体回滚** |
| **渲染** | `view <file> html` / `watch` | 内置 HTML 渲染引擎；`watch` 起实时预览服务 |
| **校验** | `validate` | 按 OpenXML Schema 校验文档 |
| **兜底** | `raw-set` / `add-part` | 任意 OpenXML 操作都能直接改 XML |
| **性能** | `open` / `save` / `close` | 常驻进程把文档留在内存，避免反复解析 |
| **重放** | `dump` → `batch` | 把子树序列化成可重放脚本（round-trip） |
| **其他** | `create` / `merge` / `import` / `refresh` / `plugins` / `mcp` / `skills` / `install` | 建空文档、模板合并、CSV 导入、域刷新、插件、MCP 服务、技能分发、一键安装 |

### 它最值得学的三个设计

1. **稳定 ID 寻址**：用 `@id=` / `@name=` / `@paraId=` 定位元素，**不用行号/序号**。文档一动，行号全变，稳定 ID 不变。
2. **分层能力（L1/L2/L3）**：L1 读 → L2 DOM 式编辑 → L3 直接改原始 XML。上层够用就别碰下层，下层保证"没有做不到的事"。
3. **原子性**：`batch` 要么全成、要么整体回滚，磁盘字节不变；配合常驻进程还能做到"内存里改完才落盘"。

## 四、架构拆解

```
          ┌──────────────────────────────────────┐
          │  CLI / MCP / skills（三种入口）        │
          └──────────────┬───────────────────────┘
                         │
          ┌──────────────▼───────────────────────┐
          │  命令层：get/set/add/remove/batch/…    │
          └──────────────┬───────────────────────┘
                         │
     ┌───────────────────▼────────────────────────┐
     │  OpenXML DOM 抽象（sheet/row/cell/range…）  │  ← 稳定 ID 在这一层
     └───────┬───────────────┬──────────────┬─────┘
             │               │              │
        ┌────▼────┐    ┌─────▼─────┐  ┌─────▼──────┐
        │ raw XML │    │ 渲染引擎   │  │ Schema 校验 │
        │ 兜底层  │    │ view html │  │  validate   │
        └─────────┘    └───────────┘  └────────────┘
```

**优点**：单二进制零依赖、格式保真好、能力面覆盖到"任何 OpenXML 操作"、对 Agent 友好（`--json`、MCP、skills 分发）。

**代价**：
- 二进制 33 MB，冷启动与渲染有可观开销（实测渲染 2.45 s）；
- 常驻进程会**持有文件锁**，别的程序在 `save`/`close` 之前读到的是旧内容；
- 命令面巨大（几十动词 × 几百元素），调用成本高，只适合被程序消费。

## 五、不足与风险（实测得出）

| # | 不足 | 实测证据 / 影响 |
| --- | --- | --- |
| 1 | **体积与冷启动** | 33,446,136 字节；`view html` 渲染一份 23 行表耗时 **2.45 s** |
| 2 | **Excel 排序拒绝合并单元格** | 对含合并区的区域执行 `sort` 会被拒绝 —— 而我们的登记表标题就是 **A1:O1 合并**，直接冲突 |
| 3 | **Excel `find` 只支持查找替换** | 不支持"查找后改格式"，无法用于批量套样式 |
| 4 | **不返回 `data-path`** | 选择集/定位信息不会回传，调用方难以稳定复现上一次操作 |
| 5 | **常驻进程文件锁** | 我们的流程是"写完立刻给用户下载"，若同时开 resident，容易读到旧文件 |
| 6 | **只覆盖 OpenXML 三件套** | 不支持老格式 `.xls`（规划部偶尔会发） |
| 7 | **对人的可读性差** | 命令与错误信息偏英文、面向机器，不可能让部里同学直接用 |
| 8 | **并发模型单一** | 单进程解析，多请求并发渲染要排队 |

> 第 2、3、5 条是**否决"用 OfficeCLI 接管写入"的决定性理由**。

| OfficeCLI 设计 | 我们借鉴后的做法 | 落地位置 | 状态 |

## 七、明确**不采纳**的部分与理由

| 不采纳 | 理由 |
| --- | --- |
| 用 OfficeCLI 替代 openpyxl 执行写入 | ① `sort` 拒绝合并单元格区域，与 A1:O1 标题直接冲突；② `find` 不支持改格式；③ 冷启动 2.45 s vs openpyxl 0.022 s（**两个数量级**） |
| 把 OfficeCLI 打进交付包强制依赖 | 33 MB 二进制，部里同学分发不便；**缺失时自动回退内置渲染**，功能不降级为零 |
| 暴露 `watch` 实时预览给同学 | 常驻进程锁文件，与"写完即下载"冲突；我们是**一次性生成静态 HTML**，更稳 |
| 用它的 `merge` 做模板填充 | 我们的需求是"在原表尾部追加两列并保留全部原格式"，不是占位符替换 |

**取舍原则**：OfficeCLI 负责**看和查**（渲染、校验），openpyxl 负责**写**（追加列、保格式）。两边各用各的长处。

## 八、实测数据（本机 · 第 5 周真实表）

文件：`2026-2027学年第一学期第5周素质拓展活动登记表(西城）（已安排二级学院）.xlsx`（23 行 × 30 列）

### 渲染对比

| 指标 | OfficeCLI `view html` | 我们的内置渲染（openpyxl） |
| --- | --- | --- |
| 耗时 | **2.45 s** | **0.022 s** |
| 产物大小 | 99.9 KB | 67.8 KB |
| `宋体` 命中 | 340 | 340 |
| 标题字号 | `font-size:24pt` ×1 | `font-size:24.0pt` ×1 |
| 正文 9pt | 342 处 | 已还原 |
| 标题合并 | `colspan="15"` ×1 | `colspan="15"` ×1 |
| 边框 | 710 处 | 687 处 |
| 外部依赖 | **0**（无 link/img/http，纯自包含） | 0 |

结论：**两者都能还原宋体与合并结构**；OfficeCLI 的产物更"Excel 原生"（细节样式更全），内置渲染快 100 倍。因此策略是 **默认走 OfficeCLI，缺失或失败时回退内置** —— 用户永远看得到预览。

### 结构校验

```

Validation passed: no errors found.
```

## 附：一句话给评审/同学解释

> OfficeCLI 是一个给 AI 用的、能高保真读写 Office 的开源命令行工具。我们**学它的三个做法**：用稳定主键而不是行号、写文件要原子并留备份、下载前先渲染体检一遍；但**没用它来写表**，因为它的排序不认合并单元格、渲染慢两个数量级、还带 33 MB 二进制。最终我们让它专职做「预览渲染 + 结构校验」，写表继续用 openpyxl —— 又快又稳，还不会把格式写坏。
